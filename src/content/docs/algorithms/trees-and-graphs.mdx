## Overview

Trees and graphs model **relationships**, not just collections. A tree captures
hierarchy and ordering; a graph captures arbitrary connections. The moment your
data has parents/children, prerequisites, paths, networks, or "things linked to
other things," you are in this territory, and the right tree or graph algorithm
turns an intractable scan into an efficient traversal. This page is about
recognizing which model fits and which traversal answers your question.

The practical payoff: balanced trees give you `O(log n)` ordered operations
(every database index leans on this), and graph algorithms answer reachability,
shortest-path, and ordering questions that no flat structure can.

## Mental model

- A **tree** is a graph with no cycles and one path between any two nodes — a
  hierarchy. You navigate it by *comparing and descending* (search trees) or
  *visiting in an order* (traversals).
- A **graph** is nodes plus edges with no such restriction — cycles, multiple
  paths, disconnected pieces. You answer questions about it by *exploring outward*
  from a start node (BFS/DFS) and tracking what you have seen.

Two questions pick almost everything:

1. **Is there inherent order/hierarchy, or arbitrary connection?** Order ->
   search tree. Hierarchy -> tree. Arbitrary links -> graph.
2. **What am I asking?** "Is it present / what is the range?" -> BST/balanced tree.
   "Shortest path / reachable?" -> graph traversal. "Valid order of dependencies?"
   -> topological sort. "Are these two in the same group?" -> union-find.

## Types / Variants

### Trees

**Binary Search Tree (BST).** Left subtree less than node, right subtree greater.
Gives `O(log n)` search/insert/delete *when balanced* — but degrades to `O(n)` (a
linked list) if you insert sorted data into a naive BST. That failure mode is why
**self-balancing** trees exist.

**Balanced trees.** Maintain `O(log n)` height under all insertions:

- **AVL trees** — strictly balanced (heights differ by at most 1). Faster lookups,
  more rotations on write. Good for read-heavy ordered data.
- **Red-black trees** — looser balance, fewer rotations on write. The default
  ordered map/set in many standard libraries (C++ `std::map`, Java `TreeMap`).
- **B-trees / B+ trees** — high-fanout (many keys per node) to minimize disk/page
  reads. The structure behind almost every relational and document **database
  index**; see *Databases & CAP* for how indexes use them.

**Tries (prefix trees).** Keys are paths of characters; shared prefixes share
nodes. Lookup is `O(L)` in the key length `L`, independent of how many keys are
stored. The structure for autocomplete, dictionaries, and **longest-prefix IP
routing** (radix tries).

**Heaps.** A heap is a tree too (covered in *Core Data Structures*) — complete
binary tree with the heap-order property, giving `O(1)` peek and `O(log n)`
push/pop. Listed here for completeness as the priority-queue backbone of Dijkstra
and friends.

**Segment trees & Fenwick (Binary Indexed) trees.** Answer **range queries**
(sum/min/max over a sub-range) with point or range updates in `O(log n)`, versus
`O(n)` for a naive recompute. A Fenwick tree is the lighter, lower-constant choice
for prefix sums; a segment tree is more general (any associative range query,
lazy range updates). Reach for these when you repeatedly query and update ranges.

### Graphs

**Representations:**

- **Adjacency list** — each node stores its neighbors. Space `O(V + E)`. Iterating
  a node's neighbors is fast. The default for **sparse** graphs (most real graphs:
  social, road, dependency).
- **Adjacency matrix** — a `V x V` grid; `matrix[i][j]` marks an edge. Space
  `O(V^2)`. Edge-existence check is `O(1)`. Use only for **dense** graphs or when
  you constantly test "is there an edge between `i` and `j`?".

**Traversals:**

- **BFS (breadth-first)** — explore level by level using a queue. Finds the
  **shortest path in an unweighted graph** and the minimum number of hops. `O(V + E)`.
- **DFS (depth-first)** — go as deep as possible using a stack/recursion. Used for
  cycle detection, topological sort, connectivity, and exhaustive search. `O(V + E)`.

**Shortest paths (weighted):**

- **Dijkstra** — non-negative edge weights. Greedily expands the closest unsettled
  node using a min-heap; `O((V + E) log V)`. The workhorse for routing and network
  cost.
- **A\*** — Dijkstra plus a heuristic that steers toward the goal. Far fewer
  expansions when you have a good admissible heuristic (e.g. straight-line distance
  in maps/games). Dijkstra is A\* with a zero heuristic.
- **Bellman-Ford** — handles **negative edge weights** and detects negative cycles;
  slower at `O(V * E)`. Use only when negative weights are real (e.g. currency
  arbitrage).

**Topological sort.** Linearizes a **directed acyclic graph (DAG)** so every edge
points forward — the valid order to do tasks given dependencies. `O(V + E)` via
DFS or Kahn's algorithm. Build systems, task schedulers, and course prerequisites
are exactly this.

**Union-Find (Disjoint Set Union).** Tracks which connected component an element
belongs to with near-`O(1)` (inverse-Ackermann) `union` and `find` after path
compression. The tool for "are these two in the same group?", dynamic connectivity,
and Kruskal's minimum spanning tree.

## When to use / When NOT

- **BST / balanced tree — use when:** you need ordered data with `O(log n)` lookup,
  range queries, or in-order iteration. **Avoid when:** you only need equality
  lookup and no order — a hash table is `O(1)`. **Never** use an unbalanced BST on
  sorted input.
- **Trie — use when:** keys share prefixes and you do prefix/autocomplete queries
  or longest-prefix match. **Avoid when:** keys are short, random, or you only need
  exact match — a hash table is simpler and lighter.
- **Segment / Fenwick tree — use when:** you repeatedly query *and* update ranges.
  **Avoid when:** the array is static (precompute a prefix-sum array, `O(1)`
  queries) or updates never happen.
- **Adjacency list — use when:** the graph is sparse (almost always). **Adjacency
  matrix — use when:** dense, or you hammer `O(1)` edge-existence checks.
- **BFS — use when:** shortest path / fewest hops in an *unweighted* graph. **DFS —
  use when:** cycle detection, topological order, connectivity, exhaustive search.
- **Dijkstra — use when:** non-negative weights. **Bellman-Ford — use when:**
  negative weights exist. **A\* — use when:** you have a good heuristic toward a
  known goal.
- **Topological sort — use when:** ordering tasks with dependencies (must be a
  DAG; a cycle means no valid order — detect it).
- **Union-Find — use when:** you incrementally merge groups and ask "same group?"
  (connectivity, Kruskal's MST). **Avoid when:** you need to *split* groups —
  union-find does not undo unions cheaply.

## Tradeoffs

| Concern | Tree-based | Graph traversal |
| ------ | ---- | ---- |
| Ordered ops (`O(log n)`) | Yes (balanced trees) | n/a |
| Equality lookup speed | `O(log n)` (slower than hash) | n/a |
| Relationship modeling | Hierarchy only | Arbitrary connections |
| Cost driver | Tree height / balance | `O(V + E)` plus heap for weighted |
| Main pitfall | Unbalanced -> `O(n)` | Wrong representation blows up space/time |

Graph-algorithm choice is dominated by **edge weights**: unweighted -> BFS;
non-negative weighted -> Dijkstra; negative weighted -> Bellman-Ford; goal-directed
with a heuristic -> A\*. Picking the wrong one is either incorrect (Dijkstra on
negative weights gives wrong answers) or needlessly slow.

## Real-world examples

- **Database indexes** (PostgreSQL, MySQL/InnoDB, SQLite) are B+ trees; the
  high fanout minimizes page reads. See *Databases & CAP*.
- **Internet routing** uses radix tries for longest-prefix match on IP addresses;
  Linux's routing table and many routers implement exactly this.
- **Google Maps and game pathfinding** use Dijkstra/A\* over road and grid graphs,
  with A\*'s heuristic (straight-line distance) cutting search dramatically.
- **Build systems** (Make, Bazel, npm) topologically sort the dependency DAG to
  decide build order and detect circular dependencies.
- **Version control and clustering** use union-find for connectivity; Kruskal's
  MST (network design, clustering) is built on it.
