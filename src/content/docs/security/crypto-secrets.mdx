## Overview

Cryptography gives you the tools to enforce **confidentiality** (encryption),
**integrity and authenticity** (signatures and MACs), and **verifiable identity
of data** — but only if used correctly, and the failure mode is silent. Code that
"encrypts" with a hardcoded key, a reused IV, or a homegrown algorithm *looks*
like it works and protects nothing. This page draws the distinctions engineers
most often blur — **symmetric vs asymmetric**, **hashing vs encryption vs
encoding** — then covers the operational reality that decides whether crypto
actually protects you: **key management and rotation**, **secrets management** in
a vault, **encryption at rest and in transit**, **digital signatures**, and the
single most important rule: **don't roll your own crypto.** TLS, the transport
case, has its own page; this is the broader toolbox.

## Mental model

**Crypto moves a secret, not removes it.** Encryption does not make data safe — it
converts the problem of "protect this data" into the problem of "protect this
key," which is smaller and more manageable but never zero. So the real
engineering is **key management**: where keys live, who can use them, and how they
rotate. A perfect cipher with a leaked or hardcoded key protects nothing.

The second clarifier, because these three are constantly confused:

- **Encoding** (base64, hex, URL) is **reversible by anyone** and provides **zero
  security** — it is for transport/representation, not secrecy. Anyone can decode
  it.
- **Hashing** is **one-way**: it maps data to a fixed digest you cannot reverse,
  used for integrity and (with a slow KDF + salt) password verifiers. You can't
  get the input back.
- **Encryption** is **reversible *with the key***: it provides confidentiality,
  and only the key-holder can recover the plaintext.

If someone says "we hashed it so it's encrypted," or "it's base64 so it's safe,"
that is a red flag.

## Types / Variants

**Symmetric encryption.** One **shared secret key** both encrypts and decrypts.
Fast and ideal for **bulk data** (files, database fields, disk). Standard:
**AES-GCM** (an AEAD mode that provides confidentiality *and* integrity together)
or **ChaCha20-Poly1305**. The hard part is *securely sharing* the key with every
party that needs it.

**Asymmetric (public-key) encryption.** A **key pair**: a **public key** anyone
may hold (encrypts / verifies) and a **private key** kept secret (decrypts /
signs). Solves the key-distribution problem — you can publish the public key —
but is **slow**, so it is used to bootstrap, not for bulk data. Standards:
**RSA**, **ECC** (Curve25519/P-256). In practice systems use **hybrid crypto**:
asymmetric to exchange a symmetric session key, then symmetric for the actual
data (exactly what TLS does).

**Hashing.** A one-way digest. Two distinct uses with different requirements:

- **Integrity / general hashing** — **SHA-256**, **SHA-3**, **BLAKE2/3**: fast, for
  checksums, content addressing, signatures. (Avoid **MD5/SHA-1** — broken for
  collision resistance.)
- **Password hashing** — **argon2id**, **bcrypt**, **scrypt**: deliberately *slow*
  and memory-hard, with a per-user **salt**. Never use a fast hash for passwords
  (covered on *Authentication*).

**Encoding (not crypto).** base64/hex/URL-encoding change *representation* for
safe transport. **No confidentiality, no integrity.** Listed here only because
it is so often mistaken for security.

**Digital signatures.** Sign a hash of the data with a **private key**; anyone
verifies with the **public key**. Provides **integrity** (tamper-evident),
**authenticity** (came from the key-holder), and **non-repudiation** (the signer
can't deny it). Used for JWTs (RS256/ES256), code signing, software updates, and
certificates. A **MAC/HMAC** is the symmetric analogue (integrity + authenticity
with a shared key, but no non-repudiation since both sides hold the key).

**Key management.** The lifecycle that makes crypto real: **generation** (strong
randomness), **storage** (HSM, KMS, or vault — never in code or config),
**access control** (least privilege on who/what can use a key), **rotation**
(periodic and on compromise, with versioning so old data stays decryptable), and
**revocation/destruction**. **Envelope encryption** is the standard pattern:
encrypt data with a per-object **data key**, encrypt that data key with a
**master key** held in a KMS — so rotating the master doesn't require re-encrypting
all the data.

**Secrets management.** Application secrets (DB passwords, API keys, tokens,
private keys) belong in a dedicated **secrets manager / vault** (HashiCorp Vault,
AWS Secrets Manager, GCP Secret Manager, Azure Key Vault), not in source code,
env files committed to git, or images. A vault adds **central storage, access
policy, audit logging, automatic rotation, and dynamic short-lived credentials**.

**Encryption at rest vs in transit.** **In transit** protects data moving over a
network — that's **TLS** (see *TLS & transport security*). **At rest** protects
stored data (disk, database, backups, object storage) so a stolen disk or
snapshot is useless without keys — disk/volume encryption, transparent database
encryption, or field-level encryption for the most sensitive columns. You want
**both**; they defend different threats.

## When to use / When NOT

- **Use symmetric (AES-GCM) when:** encrypting bulk data you control end to end
  (fields, files, disks). **Avoid asymmetric for bulk data** — it's orders of
  magnitude slower; use hybrid (asymmetric to exchange a symmetric key).
- **Use asymmetric when:** you need to distribute a public key, verify
  signatures, or can't pre-share a secret. **Avoid** for large payloads.
- **Use hashing when:** you need integrity or a one-way verifier. **Never use
  encoding (base64) as a security control** — it's reversible by anyone.
- **Use a KMS/HSM for keys and a vault for secrets when:** you have *any*
  production secret. **Never** hardcode keys/secrets in source, config, images,
  or client bundles, and **never** commit them to version control.
- **Rotate keys/secrets** on a schedule and immediately on suspected compromise;
  version them so old ciphertext stays decryptable.
- **Encrypt both at rest and in transit** for sensitive data — they defend
  different threats (stolen disk vs network eavesdropper).
- **Never roll your own crypto** — algorithms, modes, or protocols. Use vetted,
  well-maintained libraries (libsodium, the platform crypto provider, your cloud
  KMS) at the highest level of abstraction available. The bugs (IV reuse, padding
  oracles, timing leaks, weak randomness) are subtle and catastrophic.

## Tradeoffs

| Concern | Symmetric | Asymmetric |
| ------- | --------- | ---------- |
| Keys | One shared secret | Public + private pair |
| Speed | Fast (bulk data) | Slow (small payloads only) |
| Key distribution | Hard (must share secretly) | Easy (publish public key) |
| Typical use | Encrypt files/fields/disk | Key exchange, signatures |
| Examples | AES-GCM, ChaCha20-Poly1305 | RSA, ECC (Curve25519) |

| Property | Encoding | Hashing | Encryption |
| -------- | -------- | ------- | ---------- |
| Reversible? | Yes, by anyone | No (one-way) | Yes, with the key |
| Provides secrecy? | No | No | Yes |
| Provides integrity? | No | Yes (tamper-evident) | With AEAD modes |
| Use for | Transport/representation | Checksums, password verifiers | Confidentiality |
| Misuse red flag | "base64 so it's safe" | "hashed so it's encrypted" | Hardcoded key / reused IV |

## Real-world examples

- **AWS KMS, GCP Cloud KMS, and Azure Key Vault** implement **envelope
  encryption** with master keys in HSMs, giving managed rotation and audit
  logging so teams don't manage raw keys.
- **HashiCorp Vault** centralizes secrets with access policies, audit logs, and
  **dynamic short-lived credentials** (e.g., DB passwords that expire in minutes),
  shrinking the window any leaked secret is useful.
- **Signal and WhatsApp** use the **Signal Protocol** — vetted, peer-reviewed,
  *not* homegrown — for end-to-end encryption: the canonical "don't roll your own"
  done right by using expert-built primitives.
- **TLS / Let's Encrypt** is encryption in transit at internet scale; **Apple
  Advanced Data Protection** and **cloud default bucket/disk encryption** are
  encryption at rest at scale. See *TLS & transport security* for the transport
  details.
