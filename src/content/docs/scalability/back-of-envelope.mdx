## Overview

Back-of-the-envelope estimation is the skill of producing a *good-enough* number
for capacity, latency, storage, or cost in under a minute, using arithmetic you
can do in your head. Its purpose is not precision — it is to find the right
*order of magnitude* so you can size a system, spot the bottleneck, and reject
bad designs before writing any code. If a design needs 50 GB/s of bandwidth and
your network does 10 Gb/s (~1.25 GB/s), you have learned something decisive in
thirty seconds. Every system-design interview and every real capacity plan
starts here.

## Mental model

Estimation is **multiply across the request path, then compare to a hard
limit.** A request consumes time and resources at each hop; you estimate each
hop with a round number, multiply them out, and check the total against what a
single machine or link can deliver. Two anchors make this fast:

1. **The latency ladder** — a memorized table of how long each operation takes,
   each roughly an order of magnitude apart. Memory is ~100 ns, an SSD read is
   ~100 µs, a disk seek is ~10 ms, a cross-continent round trip is ~100 ms. The
   *ratios* are what matter: memory is ~1000x faster than disk; staying in RAM
   (or cache) vs hitting disk or network is the single biggest lever you have.
2. **Round everything.** A day is ~$10^5$ seconds (86,400 ≈ 100,000). A million
   users at 10 requests/day is $10^7$ requests/day ≈ 100 QPS average. Powers of
   ten and powers of two replace a calculator. Accuracy to one significant
   figure is the goal; being within 2–3x of reality is a success.

## Types / Variants

The numbers and conversions worth committing to memory.

**Latency numbers every engineer should know** (order-of-magnitude, modern
hardware):

| Operation | Latency | In human terms (×10⁹) |
| --------- | ------- | --------------------- |
| L1 cache reference | ~1 ns | 1 s |
| Branch mispredict | ~3 ns | 3 s |
| L2 cache reference | ~4 ns | 4 s |
| Mutex lock/unlock | ~17 ns | 17 s |
| Main memory reference | ~100 ns | ~2 min |
| Compress 1 KB (Snappy) | ~2 µs | ~30 min |
| Read 1 MB sequentially from RAM | ~3–10 µs | ~1–3 h |
| SSD random read | ~16–100 µs | ~5–30 h |
| Round trip within a datacenter | ~0.5 ms | ~6 days |
| Read 1 MB sequentially from SSD | ~50–1000 µs | ~1 day |
| Disk (HDD) seek | ~3–10 ms | ~1–4 months |
| Read 1 MB sequentially from HDD | ~20–30 ms | ~8 months |
| Round trip CA → Netherlands → CA | ~150 ms | ~5 years |

The takeaways that drive design: **memory is ~100x faster than SSD and ~100,000x
faster than a cross-continent round trip; sequential is vastly faster than
random; and a network round trip dwarfs almost any local computation.** This is
*why* caching, batching, sequential I/O, and co-location win.

**Powers of two — data sizes:**

| Power | Exact | Approx | Name |
| ----- | ----- | ------ | ---- |
| 2¹⁰ | 1,024 | ~10³ | 1 KB |
| 2²⁰ | 1,048,576 | ~10⁶ | 1 MB |
| 2³⁰ | ~1.07×10⁹ | ~10⁹ | 1 GB |
| 2⁴⁰ | ~1.10×10¹² | ~10¹² | 1 TB |
| 2⁵⁰ | ~1.13×10¹⁵ | ~10¹⁵ | 1 PB |

So a 64-bit (8-byte) integer × 1 billion rows ≈ 8 GB; a 2³² ID space ≈ 4 billion
values; 2⁶⁴ is ~1.8×10¹⁹, effectively unbounded for IDs.

**Time conversions worth memorizing:**

- 1 day ≈ 86,400 s ≈ **10⁵ s** (the single most useful estimation shortcut).
- 1 month ≈ 2.5×10⁶ s; 1 year ≈ 3.15×10⁷ s ≈ **π×10⁷ s**.
- "X per day" → QPS: divide by 10⁵. So **100,000 events/day ≈ 1 QPS**; 1
  billion/day ≈ 10⁴ QPS average.

**Peak vs average.** Traffic is never flat. A common rule: **peak ≈ 2–3× the
average** for steady consumer apps, and far more for spiky events (flash sales,
launches, sports). Always size for peak, not average — provision to **peak QPS =
average QPS × peak factor**, then add headroom (often ×2) for safety and growth.

**The 80/20 rule (and worse).** Access is skewed: ~20% of the data gets ~80% of
the traffic, and at scale it is often 1/99. This is what makes caching work
(cache the hot 20%, serve most reads from RAM) and what creates **hot keys/hot
shards** (the celebrity problem — see **Sharding & partitioning**). Always ask
"how skewed is the access?" — it changes cache sizing and shard design.

## When to use / When NOT

- **Use when:** kicking off any design to find the dominant resource (compute,
  storage, bandwidth, or QPS); deciding whether something fits on one machine or
  must be distributed; sanity-checking a vendor quote or a teammate's claim; or
  in an interview, to justify every architectural choice with a number.
- **Avoid / don't over-invest when:** the decision doesn't hinge on scale (a CRUD
  app for 100 internal users needs no QPS math); you'd be false-precise (six
  significant figures from guessed inputs is theatre); or real measurements
  exist — a load test beats any estimate. Estimation guides *what to measure*; it
  never replaces measuring in production.

## Tradeoffs

| Choice | Pros | Cons |
| ------ | ---- | ---- |
| Round to 1 sig-fig | Fast, mental, good enough for sizing | Can be 2–3x off — wrong for billing/SLA |
| Size for peak (×2–3) | Survives spikes, no brownouts | Idle capacity, higher cost (mitigated by autoscaling) |
| Size for average | Cheapest | Falls over at peak — usually the wrong call |
| Estimate before building | Catches infeasible designs early | Garbage-in if input assumptions are wrong |
| Measure instead | Ground truth | Needs a running system + load to measure |

The meta-tradeoff: estimation trades accuracy for speed. Its value is in the
*orders of magnitude*, so guard the **inputs** (DAU, request rate, object size,
read/write ratio, retention) — those assumptions, not the arithmetic, are where
estimates go wrong.

## Real-world examples

- **Jeff Dean's "Numbers Everyone Should Know"** (Google) is the origin of the
  latency-ladder table; every system-design curriculum reproduces it.
- **System-design interviews** at Google, Meta, Amazon, and others explicitly
  grade back-of-the-envelope estimation — candidates are expected to derive QPS,
  storage, and bandwidth before drawing a box.
- **Capacity planning** teams size fleets this way first (estimate peak QPS ×
  per-host capacity → host count), then confirm with load tests before
  committing budget.
