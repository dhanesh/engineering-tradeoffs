## Overview

**RPC (Remote Procedure Call)** makes a network call *look like* a local function call:
you invoke `client.GetUser(id)` and the framework marshals the arguments, ships them over
the wire, runs the procedure on a remote server, and returns the result. **gRPC** is the
modern, dominant RPC framework: it defines services and messages in **Protobuf** (a compact
binary schema), generates strongly-typed client and server **stubs** in a dozen languages,
and runs over **HTTP/2** to get multiplexed, bidirectional **streaming**. The result is the
lowest-latency, smallest-payload, most strongly-contracted option for **internal,
service-to-service** traffic — at the cost of being binary (not human-debuggable) and not
natively callable from a browser.

## Mental model

**The schema generates the code; the procedure call hides the network.** You write a
`.proto` file once — the **single source of truth** for both sides — and code generation
produces type-safe client and server stubs. Calling a remote method then looks and feels
like calling a local one, with the serialization, framing, and transport handled for you.
Two properties fall out of this:

- **Protobuf is a binary, schema-driven format**: fields are identified by **tag numbers**,
  not names, so payloads are tiny and parsing is fast — but you *need* the schema to read
  the bytes (no curl-and-eyeball). Schema evolution is governed by keeping tag numbers
  stable.
- **HTTP/2 is the transport**, so a single connection multiplexes many concurrent calls and
  supports **streaming** in both directions — gRPC isn't limited to request/response.

## Types / Variants

**Protobuf (the IDL).** Strongly-typed messages and services in a `.proto`. Backward/forward
compatibility rules: **never reuse or change a field's tag number**, add new fields as
optional, and treat unknown fields as pass-through. This is what lets old and new clients/
servers interoperate during a rollout.

**The four call types (HTTP/2 streaming):**

- **Unary** — one request, one response. The familiar RPC; replaces a REST `GET`/`POST`.
- **Server streaming** — one request, a **stream** of responses (live feed, large result
  set, progress updates).
- **Client streaming** — a **stream** of requests, one response (uploading chunks, batching
  telemetry).
- **Bidirectional streaming** — both sides stream independently over the one connection
  (chat, real-time sync, long-lived control channels). This is gRPC's headline capability
  and where it clearly beats request/response REST.

**Code generation & stubs.** `protoc` (with language plugins) generates the message classes
and the client/server stubs, so the contract is enforced *at compile time* in every
language — a strong guarantee REST/JSON can't make without extra tooling.

**Deadlines, cancellation, and metadata.** Every gRPC call carries a **deadline** (an
absolute time by which it must complete); when it passes, the call is cancelled **end to
end** — the server learns the client gave up and can stop work, which prevents wasted
compute and cascading overload. (Contrast bare REST, where a client timeout doesn't
inherently tell the server to stop.) Calls also carry **metadata** (key/value headers, e.g.
auth tokens) and rich **status codes** (`OK`, `DEADLINE_EXCEEDED`, `UNAVAILABLE`,
`RESOURCE_EXHAUSTED`, …) that map cleanly onto retry policies.

**When binary RPC beats REST/GraphQL.** For **internal east-west** traffic: Protobuf
payloads are several times smaller than JSON and parse faster; HTTP/2 multiplexing avoids
connection sprawl; the generated, strongly-typed contract eliminates a class of integration
bugs; deadlines and streaming are first-class. At high call volume between services these
add up to materially lower latency, CPU, and bandwidth than JSON-over-HTTP.

**The browser problem & gRPC-Web gateway.** Browsers can't speak raw gRPC (no access to the
HTTP/2 frames gRPC needs, and limited streaming control). **gRPC-Web** plus a proxy
(Envoy, or a gateway) bridges browser ↔ gRPC; alternatively a **grpc-gateway** transcodes
JSON/REST on the edge into gRPC internally — so you expose REST/JSON to the public and run
gRPC behind it. This "REST at the edge, gRPC inside" pattern is extremely common.

## When to use / When NOT

- **Use gRPC when:** internal service-to-service traffic where latency, throughput, and
  payload size matter; polyglot services that benefit from one generated contract;
  streaming (server/client/bidi) is needed; you want end-to-end deadlines and cancellation;
  you're building a microservice mesh.
- **Avoid gRPC when:** the client is a browser with no proxy budget (use REST, or gRPC-Web/
  transcoding); you need human-readable, curl-able payloads and easy ad-hoc debugging; the
  consumers are arbitrary third parties who expect REST/JSON; or HTTP caching of responses
  is central to the design (gRPC has none).
- **Default placement:** REST or GraphQL at the **public edge**; gRPC for the **internal**
  calls behind it.

## Tradeoffs

| Concern | gRPC | REST | GraphQL |
| ------- | ---- | ---- | ------- |
| Payload | Protobuf (binary, smallest) | JSON (text) | JSON |
| Transport | HTTP/2 (multiplexed) | HTTP/1.1 or 2 | HTTP (one POST) |
| Streaming | Server/client/bidi, first-class | SSE/long-poll bolt-ons | Subscriptions (WS/SSE) |
| Contract | `.proto` → generated stubs (compile-time) | OpenAPI (optional) | Typed schema |
| Browser | Needs gRPC-Web proxy | Native | Native |
| Human-debuggable | No (binary) | Yes (curl) | Mostly |
| HTTP caching | None | First-class | Hard |
| Best fit | Internal east-west, low latency | Public/partner CRUD | Client aggregation |

## Real-world examples

- **Google** runs internal services on **Stubby** (gRPC's predecessor) and open-sourced gRPC;
  Protobuf is the lingua franca of its service fleet.
- **Netflix, Square, and Dropbox** use gRPC for internal service-to-service traffic to cut
  east-west latency and payload size versus JSON.
- **Envoy** is the standard proxy for **gRPC-Web** transcoding and for putting gRPC services
  behind a mesh/gateway.
- **Kubernetes, etcd, and CockroachDB** expose gRPC APIs for their control/data planes,
  relying on Protobuf's schema-evolution rules for rolling upgrades.
