## Overview

A CDN (Content Delivery Network) is a globally distributed fleet of cache servers —
**points of presence (PoPs)** — placed near users, so a request is served from a
nearby city instead of crossing oceans to your origin. It is the outermost cache
layer, and the cheapest place to absorb load: every request a PoP serves is a request
your origin never sees. Beyond static assets, modern CDNs cache dynamic responses,
run compute at the edge, and absorb traffic spikes and DDoS volume. This page covers
how CDNs decide what to cache (the HTTP cache-control model), how they stay fresh
without stampeding your origin (`stale-while-revalidate`), and when pushing logic to
the edge pays off.

## Mental model

A CDN is **HTTP caching, replicated to hundreds of locations, controlled by your
response headers.** You do not configure the cache imperatively — you *describe each
response's cacheability* with headers, and every PoP independently honors that
description. The two levers are:

- **Freshness:** `Cache-Control: max-age` / `s-maxage` says how long a PoP may serve a
  response without re-checking the origin.
- **Validation:** `ETag` / `Last-Modified` let a PoP cheaply ask "has this changed?"
  via a conditional request; an unchanged resource returns `304 Not Modified` with no
  body, saving bandwidth.

The key distinction: `max-age` controls *private* (browser) caches, `s-maxage`
controls *shared* (CDN) caches — so you can cache aggressively at the edge while
keeping browsers conservative. Everything else (purge APIs, edge compute, SWR) builds
on this header-driven core.

## Types / Variants

**Static asset caching.** Images, CSS, JS, fonts, video segments. The bread and
butter: long `max-age` (often a year) combined with **content-hashed filenames**
(`app.4f2a9.js`) so a new deploy is a new URL — instant, race-free invalidation by
never reusing a URL.

**Cacheable dynamic content.** HTML and API responses that are the same for many
users for a short window. Cache for seconds-to-minutes with `s-maxage` to shield the
origin during spikes (a homepage cached for 10s serves one origin hit per 10s no
matter the traffic).

**Cache-control directives that matter.**
- `public` / `private` — may a shared (CDN) cache store it?
- `max-age` (browser) / `s-maxage` (CDN) — freshness lifetime.
- `no-cache` — store it, but *revalidate* before each use (not "don't cache").
- `no-store` — never cache (genuinely private/sensitive responses).
- `must-revalidate` — once stale, do not serve without revalidating.
- `stale-while-revalidate=N` — serve stale up to N seconds *while* asynchronously
  refreshing in the background (no latency cliff, no origin stampede).
- `stale-if-error=N` — serve stale if the origin is down (resilience).
- `Vary` — cache separate copies per header (e.g. `Vary: Accept-Encoding`); a broad
  `Vary` (like `Cookie`) destroys hit rate by fragmenting the cache.

**Invalidation at the edge.** TTL expiry (default), **purge/ban APIs** (explicit, but
propagation across PoPs takes time), **surrogate keys / cache tags** (tag responses,
purge a whole tag at once — Fastly's signature feature), and **versioned URLs** (the
cleanest: never invalidate, just change the URL).

**Edge compute.** Run code at the PoP — Cloudflare Workers, Fastly Compute@Edge,
AWS Lambda@Edge / CloudFront Functions, Vercel Edge. Use it for request routing,
A/B testing, auth checks, header rewriting, personalization, and assembling responses
from cached fragments — all without a round trip to origin. The edge becomes a
programmable cache, not just a static one.

## When to use / When NOT

- **Use a CDN when:** you serve static or cacheable content to a geographically
  distributed audience; you need to offload origin traffic and egress cost; you must
  absorb spikes or DDoS volume; or latency to far-away users matters. **Avoid (or
  bypass the cache) when:** content is per-user and uncacheable (set `private`/
  `no-store`), strictly consistent and stale copies cause correctness bugs, or the
  audience is single-region and co-located with origin (a CDN adds a hop for little
  gain).
- **Use `stale-while-revalidate` when:** a brief staleness window is acceptable and
  you want zero refresh-latency and origin-stampede protection. **Avoid SWR for**
  content that must never be even slightly stale (post-payment confirmation, security
  decisions).
- **Use edge compute when:** logic must run close to users with no origin round trip
  (routing, auth, personalization, fragment assembly). **Avoid when:** the logic needs
  your primary database or heavy/stateful processing — that belongs at origin.

## Tradeoffs

| Concern | With a CDN | Without (origin-only) |
| ------- | ---------- | --------------------- |
| Latency (far users) | Low (served from nearby PoP) | High (round trip to origin) |
| Origin load | Greatly reduced (offloaded) | Full load on origin |
| Freshness | Bounded by TTL / purge lag | Always fresh |
| Invalidation | Hard (purge propagation across PoPs) | Trivial (one source) |
| Cost | Cheaper egress, absorbs spikes | Higher origin + egress cost |
| Complexity | Header tuning, purge, Vary discipline | Simpler, but doesn't scale geo |

## Real-world examples

- **Cloudflare** and **Fastly** front a large fraction of the web; Fastly pioneered
  instant **surrogate-key** purges and built on Varnish (VCL) for programmable edges.
- **Netflix Open Connect** places caching appliances inside ISPs so video streams from
  as close to the viewer as physically possible.
- **Vercel / Next.js ISR** (Incremental Static Regeneration) is `stale-while-revalidate`
  productized: serve a cached page instantly, regenerate it in the background.
- **Cloudflare Workers** and **Lambda@Edge** run auth, A/B tests, and personalization
  at the PoP, turning the CDN into a programmable application edge.
