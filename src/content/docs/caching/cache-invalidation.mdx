## Overview

"There are only two hard things in computer science: cache invalidation and naming
things." The joke endures because invalidation is genuinely hard: a cache is a copy
of the truth, and the moment the truth changes, every copy is a potential lie. Get
invalidation wrong and you serve stale data (a correctness bug that's invisible
until it isn't) or you stampede your backend when many entries expire at once.
Invalidation is where caching projects succeed or quietly fail. This page covers the
mechanisms for removing/refreshing stale entries and the protections against the
failure modes invalidation itself creates.

## Mental model

Invalidation answers one question — *when does a cached copy stop being trusted?* —
and you have exactly two families of answers:

- **Time-based (pull):** the copy is trusted for a fixed duration (TTL), then
  re-validated. Simple, self-healing, eventually consistent. You accept staleness up
  to the TTL in exchange for never having to track writes.
- **Event-based (push):** the copy is trusted until a write explicitly invalidates
  it. Fresher (near-zero staleness) but requires you to *reliably* propagate every
  write to every cache — a missed event means a permanently stale entry.

Most production systems use **both**: event-based invalidation for freshness, with a
TTL as a safety net so a missed event self-corrects eventually. Then, layered on
top, you need **stampede protection** to survive the moment many entries become
invalid at once.

## Types / Variants

**TTL (time-to-live).** Each entry expires after a fixed duration; the next read
misses and repopulates. Dead simple, no write coordination, self-healing. Tradeoff:
you serve data up to one TTL stale, and synchronized TTLs cause stampedes. Mitigate
with **jitter** (randomize each TTL ±10–20%) so expiries spread out.

**Explicit / event-based invalidation.** On a write, publish an event (or directly
`DEL` the key) so caches drop the stale entry. Near-zero staleness. The hard parts:
delivery reliability (use a durable bus or CDC), fan-out to *every* cache replica,
and the populate/invalidate race (a slow reader can re-insert a stale value *after*
the delete).

**Write-through invalidation.** Because a write-through cache updates the cache and
DB together, the cache is never stale for written keys — invalidation is implicit in
the write path. (See *Caching strategies*.) Clean, at the cost of write latency.

**Versioned keys (key namespacing).** Encode a version/generation into the cache key
(`user:42:v7` or `products:list:{etag}`). To invalidate, bump the version — old keys
are instantly unreachable and age out by eviction; no delete needed. Excellent for
invalidating *collections* (bump a "namespace version" to wipe all derived keys at
once) and immune to the populate/invalidate race because writers and readers never
touch the same key. Cost: orphaned old-version entries linger until evicted.

**Stampede / thundering-herd protection.** When a hot key expires, thousands of
concurrent requests miss simultaneously and all hit the backend ("dogpile"). Three
defenses:
- **Locking / mutex (single-flight):** the first miss acquires a lock and recomputes;
  others wait for the result or briefly serve the stale value. One backend call
  instead of thousands.
- **Request coalescing (single-flight):** in-process, collapse concurrent identical
  misses into one upstream call and share the result (Go's `singleflight`, DataLoader).
- **Early / probabilistic recompute (XFetch):** refresh a hot key *before* it
  expires, with a probability that rises as expiry nears, so one lucky request
  refreshes it while others still serve the fresh-enough value. Avoids any hard
  expiry cliff.

**Negative caching.** Cache the *absence* of a result (404s, empty lookups, "user not
found") for a short TTL. Without it, every request for a nonexistent key is a
guaranteed miss that hammers the DB — a common amplifier in penetration/abuse
traffic. Keep negative TTLs short so a created-later record appears promptly.

## When to use / When NOT

- **TTL — use when:** bounded staleness is acceptable and you want zero write
  coordination; always add jitter. **Avoid as the only mechanism when:** you need
  near-real-time freshness.
- **Event-based — use when:** freshness matters and you can deliver write events
  reliably (CDC, durable bus). **Avoid when:** delivery is best-effort and a missed
  event (permanent staleness) is unacceptable without a TTL backstop.
- **Versioned keys — use when:** you invalidate whole collections, want to dodge the
  populate/invalidate race, or want atomic "flip a version" semantics. **Avoid
  when:** memory is tight and orphaned versions can't be afforded.
- **Stampede protection — use when:** any key is hot enough that simultaneous misses
  could overload the backend (almost always, at scale). **Avoid skipping it** for
  hot keys — this is the most common production cache outage.
- **Negative caching — use when:** misses for nonexistent keys are common or abusable.
  **Avoid long negative TTLs** that hide newly-created records.

## Tradeoffs

| Mechanism | Staleness | Write coordination | Complexity | Main failure mode |
| --------- | --------- | ------------------ | ---------- | ----------------- |
| TTL | Up to one TTL | None | Lowest | Synchronized-expiry stampede |
| Event-based | Near-zero | High (reliable delivery) | High | Missed event ⇒ permanent stale |
| Write-through | Zero (written keys) | In write path | Medium | Higher write latency |
| Versioned keys | Zero (new version) | Bump on write | Medium | Orphaned old versions linger |
| Stampede protection | n/a (protects refill) | n/a | Medium | Lock contention if misconfigured |
| Negative caching | Up to negative TTL | None | Low | Hides newly-created records |

## Real-world examples

- **Facebook's "leases"** (NSDI '13) solve the populate/invalidate race: a miss
  hands out a lease token, and a stale set without a valid lease is rejected.
- **Varnish / Fastly** ship **stale-while-revalidate** and request coalescing
  natively so an expired hot object is served stale while one request refreshes it.
- **Rails / Django** use versioned (key-based) cache expiration — the model's
  `updated_at` is baked into the key, so any update produces a fresh key with no
  explicit purge.
- **Go's `singleflight`** and **Facebook/Meta's DataLoader pattern** are the standard
  request-coalescing tools against dogpile.
- **Probabilistic early expiration (XFetch)** comes from the "Optimal Probabilistic
  Cache Stampede Prevention" paper and is implemented in several Redis client
  libraries.
