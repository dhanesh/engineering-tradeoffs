## Overview

An in-process cache is the fastest cache there is — but it is *local*: each app
instance has its own copy, none of them shared, all of them lost on restart, and a
40-node fleet means 40 independent caches with 40 separate hit rates and 40 chances
to be stale. A **distributed cache** is a separate, networked tier (Redis,
Memcached) that every app instance shares. You pay one network round trip (~0.2–1 ms)
to gain a single, large, shared, restart-surviving cache. This page covers how to
build that tier: which engine, how to spread data across nodes, how to replicate for
availability, and how to survive hot keys.

## Mental model

A distributed cache is a **partitioned hash table living across a fleet of nodes,
reached over the network.** Two questions define its design:

1. **Placement — which node holds a given key?** Naive `hash(key) % N` is a trap:
   change `N` (add/remove a node) and *almost every* key remaps, emptying the cache
   in one stroke. **Consistent hashing** (a hash ring) fixes this — adding/removing a
   node remaps only `1/N` of keys. Virtual nodes smooth out the distribution.
2. **Topology — where does the caching logic live?** **Look-aside** (the app talks
   to cache and DB separately) versus **inline/read-through** (the cache sits in the
   data path and loads from the DB itself).

On top of placement sits **replication** (copies for availability/read-scaling) and
the **hot-key problem** (one key so popular that its single owning node is
overwhelmed regardless of how well you partitioned).

## Types / Variants

**Redis vs Memcached — the core engine choice.**
- **Memcached:** a pure, multithreaded, in-memory key→blob store. Values are opaque
  bytes; the only operations are get/set/delete/incr. Brutally simple, scales reads
  across cores, slab allocator minimizes fragmentation. No persistence, no
  replication (client-side sharding only), no rich types. The right tool when you
  want a fast, dumb, horizontally-sharded blob cache.
- **Redis:** an in-memory *data-structure* server — strings, hashes, lists, sets,
  sorted sets, streams, HyperLogLog, bitmaps, geo, plus Lua scripting, pub/sub,
  transactions, persistence (RDB snapshots + AOF log), replication, and **Redis
  Cluster** (built-in sharding with 16384 hash slots). Single-threaded for commands
  (so a slow command blocks others; Redis 6+ adds threaded I/O). The right tool when
  you need data structures, atomic ops, durability, or built-in clustering — i.e.
  most of the time today.

**Partitioning (sharding).** Spread keys across nodes for capacity and throughput.
Consistent hashing (Memcached clients, Cassandra) or fixed hash slots (Redis Cluster)
decide ownership. Multi-key operations are constrained to a single shard (Redis uses
**hash tags** `{user42}:...` to co-locate related keys).

**Replication.** Each shard has a primary plus replicas. Buys **read scaling**
(serve reads from replicas) and **availability** (promote a replica on primary
failure). Redis replication is *asynchronous* — a primary can ack a write then crash
before replicating it, so failover can lose recent writes (acceptable for a cache,
fatal for a ledger).

**Topology — look-aside vs inline.**
- **Look-aside (cache-aside):** app reads cache; on miss reads DB and populates. The
  cache is a dumb store; the app owns the logic. Most common; the cache failing
  degrades to slow-but-correct DB reads.
- **Inline (read-through/write-through):** the cache is in the data path and loads
  from the DB itself. Simpler app code; but a cache outage can break the read path
  unless it fails open.

**Hot keys.** One key (a celebrity user, a flash-sale SKU) drawing disproportionate
traffic overwhelms its single owning node. Fixes: **client-side local caching** of
that key for a few seconds, **key splitting/replication** (`hotkey:0..N` fanned
across nodes), or a small in-process layer in front of the distributed tier.

## When to use / When NOT

- **Use a distributed cache when:** multiple app instances must share cached state
  (sessions, shared hot data); the cache must survive app restarts and deploys; the
  dataset exceeds a single process's heap; or you need cache state independent of app
  scaling. **Avoid when:** the data is cheap to recompute per-instance and an extra
  network hop isn't worth it (use in-process), or the cache is a single point of
  failure you cannot make redundant.
- **Choose Redis when:** you need data structures, atomic counters, pub/sub, Lua,
  persistence, or built-in clustering — or simply want the richer, batteries-included
  default. **Avoid Redis when:** you genuinely only need a fast multithreaded blob
  cache and want to saturate many cores per node with minimal features.
- **Choose Memcached when:** pure, multithreaded, horizontally-sharded blob caching of
  large simple objects is all you need. **Avoid when:** you need any of persistence,
  replication, data structures, or server-side clustering.

## Tradeoffs

| Concern | Look-aside | Inline (read/write-through) |
| ------- | ---------- | --------------------------- |
| App complexity | App owns load logic | Centralized in cache |
| Cache outage behavior | Degrades to DB (fails open) | Can break read path unless fail-open |
| Consistency control | Per-call, flexible | Uniform, less granular |
| Best for | General web/API caching | Uniform access via one library |

| Concern | Memcached | Redis |
| ------- | --------- | ----- |
| Data model | Opaque blobs | Rich data structures |
| Threading | Multithreaded | Single-threaded commands (+threaded I/O) |
| Persistence | None | RDB + AOF |
| Clustering / replication | Client-side sharding | Redis Cluster + replicas |
| When to pick | Simple blob cache, many cores | Default; structures, durability, clustering |

## Real-world examples

- **Facebook** runs one of the largest Memcached deployments on earth as a look-aside
  tier in front of MySQL, with regional pools and leases (NSDI '13).
- **Netflix EVCache** wraps Memcached with replication and zone-aware topology for
  resilient sub-millisecond personalization reads across AWS regions.
- **Twitter / X** used a heavily-modified Memcached (Twemcache) and Twemproxy for
  sharding/proxying at scale.
- **GitHub, Shopify, Stack Overflow** lean on Redis for sessions, fragment caching,
  rate limiting, and job queues — exploiting the data structures, not just get/set.
- **AWS ElastiCache** and **Azure Cache for Redis** are the managed forms most teams
  actually deploy.
