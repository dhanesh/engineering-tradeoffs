## Overview

A mobile app does not run on infrastructure you control. It is a frozen binary, gatekept by
a store, running on an untrusted device, used by people on a long tail of OS and app
versions. That reality creates a cluster of concerns the web never forces on you all at
once: **you cannot hotfix native code on demand** (a store review stands between you and
every fix), **you must ask the OS and user for every capability** (permissions/privacy),
**the binary can be inspected and tampered with** (security), and **a large fraction of
users will be on old versions for months** (versioning/forced upgrade). Handling these well
is the difference between an app you can operate safely and one bug away from a multi-week
fire you can't put out. This page covers the release, security, privacy, and lifecycle
concerns that are unique to shipping on a platform you don't own.

## Mental model

**You ship to a gatekept store, an untrusted device, and a version-fragmented user base —
so build for slow rollback, zero device trust, and version skew from day one.** Three
durable consequences:

- **You can't take it back instantly.** A native bug is frozen until a new build clears
  review and users update. Therefore: roll out in *phases* (catch issues at 1–5% before
  100%), keep risky behavior behind *server-side flags* you can flip without a release, and
  push JS/bundle fixes *over the air* where the platform allows it.
- **The device is the adversary's lab.** Anyone can decompile your binary, inspect traffic,
  and run on a jailbroken/rooted device. Therefore: *the server is always the authority*, no
  secrets live in the app, sensitive data goes in the *Keychain/Keystore*, and you *pin
  certificates* and detect tampering as defense-in-depth — never as your only line.
- **Users are scattered across versions.** Your newest API and oldest client must coexist.
  Therefore: version your APIs, gate breaking changes behind *forced upgrade*, and degrade
  gracefully on old clients.

## Types / Variants

**Release and rollout.**

- **App-store review** — Apple's App Store and Google Play review each submission against
  policy; approval takes hours to days and can be rejected. Plan lead time; you cannot ship
  on a whim.
- **Phased / staged rollout** — release to a growing percentage (e.g. Play's staged
  rollout, App Store phased release) so you can halt before a bug reaches everyone.
- **Code push / OTA (JS only)** — React Native / Expo Updates (and the now-retired
  Microsoft CodePush) can replace the *JS bundle* over the air *without store review* — but
  **only JS/assets, never native code**, and within store policy limits. Native changes still
  require a store release.
- **Server-side feature flags / kill switches** — flip behavior without any release; the
  single most important operational lever on mobile, since the binary itself can't be patched
  fast.

**Permissions & privacy.** Runtime permission prompts (camera, location, contacts,
notifications, tracking), the principle of least privilege (ask only when needed, in
context), Apple's **App Tracking Transparency (ATT)** and privacy "nutrition labels," Android
runtime permissions and scoped storage, and data-minimization/consent obligations
(GDPR/DPDP-style — directly relevant to fintech/lending data).

**Security.** Secure storage in the **Keychain (iOS)** / **Keystore (Android, hardware-backed
where available)** for tokens and keys; **certificate / public-key pinning** to resist MITM;
**jailbreak/root detection** and tamper/integrity checks (App Attest, Play Integrity) as
defense-in-depth; biometric gating (Face ID / fingerprint) for sensitive actions; never
embedding secrets in the binary. The server enforces authorization regardless of client
claims.

**Deep linking.** URL schemes and **Universal Links (iOS) / App Links (Android)** that open
a specific screen with the right back stack, supporting marketing, sharing, and OS-level
navigation; deferred deep links route a not-yet-installed user through install to the
intended screen.

**Observability.** Crash reporting and stability (Crashlytics, Sentry, Bugsnag, Xcode
Organizer), product analytics (events, funnels — e.g. Mixpanel/Amplitude), and performance
monitoring (cold start, jank, ANRs). Because you can't watch logs on a million devices, you
*instrument* and aggregate.

**Accessibility.** Screen readers (VoiceOver/TalkBack), Dynamic Type / font scaling,
sufficient contrast, touch-target sizing, and semantic labeling — both an ethical/legal
requirement and a quality bar.

**Versioning & forced upgrade.** API versioning, minimum-supported-version policy, *forced
upgrade* gates that block clients too old to run safely (essential for security or breaking
changes), and "soft" nudges for recommended updates.

## When to use / When NOT

- **Phased rollout — use when:** any release with real risk (most). **Avoid skipping it**
  except for trivial, reversible changes — it's the cheapest safety net you have.
- **Code push (OTA) — use when:** you must fix a *JS-level* bug fast or ship a config/asset
  change without waiting on review. **Avoid for:** native changes (impossible) and anything
  that violates store policy on materially changing the app outside review.
- **Certificate pinning — use when:** the app handles sensitive data (auth, payments,
  finance) and you can operate a pin-rotation process. **Avoid when:** you can't manage pin
  rotation — a stale pin bricks the app for everyone until they update.
- **Forced upgrade — use when:** an old client is insecure, broken against a new API, or a
  legal/compliance risk. **Avoid for:** routine updates — gratuitous forced upgrades anger
  users; reserve it for genuine must-upgrade cases.
- **Jailbreak/root detection — use when:** as one layer of defense-in-depth for high-stakes
  apps. **Avoid relying on it** as a real security boundary — it's bypassable; the server
  must still enforce everything.

## Tradeoffs

| Concern | Lever | Tradeoff |
| ------- | ----- | -------- |
| Slow native rollback | Phased rollout + flags | Slower full ship; needs flag discipline |
| Native can't hotfix | Code push (JS only) | JS-only; store-policy limits |
| Untrusted device | Keychain/Keystore, pinning | Pin rotation risk; server still authoritative |
| MITM | Cert/key pinning | Stale pin can brick app; rotation ops |
| Version skew | API versioning + forced upgrade | Forced upgrades annoy users; reserve them |
| Privacy/consent | Least-privilege, ATT, labels | Friction; lower opt-in; compliance work |
| Can't watch devices | Crash + analytics instrumentation | Data/privacy cost; instrumentation effort |

## Real-world examples

- **Google Play staged rollout and App Store phased release** are standard practice — teams
  ship to a small percentage, watch crash-free rates, and halt on regressions.
- **React Native / Expo OTA updates** let teams patch JS-level bugs in hours instead of a
  multi-day review cycle.
- **Banking and fintech apps** (the GrayQuest domain) pin certificates, store tokens in the
  Keychain/Keystore, gate actions behind biometrics, use Play Integrity / App Attest, and
  force-upgrade insecure clients — with the server as the sole authorization authority.
- **Uber, Instagram, and most large apps** run feature flags and kill switches so behavior
  can change without a release, and instrument heavily with Crashlytics/Sentry-style tooling.
