## Overview

Mobile app architecture answers one recurring question: **where does state live, who is
allowed to change it, and how does the UI stay in sync with it as the OS pauses, kills,
and recreates your process?** A phone app is an event-soaked, asynchronous, interruptible
program — taps, network responses, sensor updates, lifecycle callbacks, and OS kills all
race to mutate shared state. Without a disciplined architecture you get the classic
mobile failure mode: stale screens, lost edits, crashes on rotation, and bugs that only
reproduce after backgrounding. The patterns here (MVVM, MVI, TCA, Clean) all exist to
tame that chaos by making **state flow predictable** and **logic testable apart from the
UI**.

## Mental model

**Separate what the user sees from what is true, and make state flow in one direction.**
Three layers, and one dominant principle:

- **UI layer** — renders a *view state* and emits *user intents/events*. Dumb and
  replaceable; holds no business logic.
- **Presentation layer** (ViewModel / Store / Reducer) — holds the screen's state, turns
  intents into state changes, and survives configuration changes. This is the testable
  heart of the app.
- **Domain + data layer** — use cases, repositories, local stores, and network. Knows
  nothing about the UI.

The dominant principle is **unidirectional data flow (UDF)**: *state flows down* (a single
observable state object renders the UI) and *events flow up* (the UI emits intents that
produce a new state). State is the single source of truth; the UI is a pure function of
it. This is what makes the screen trivially restorable and the logic trivially testable —
you can replay a sequence of events and assert on the resulting state with no UI at all.

## Types / Variants

**MVVM (Model–View–ViewModel).** The platform default (Android's ViewModel + StateFlow;
iOS SwiftUI's `@Observable`/`ObservableObject`). The ViewModel exposes observable state
and methods; the View binds to it. Pragmatic and well-supported, but plain MVVM can drift
toward multiple mutable properties and ad-hoc mutations — discipline (or MVI) keeps it
unidirectional.

**MVI (Model–View–Intent).** Strict UDF: a *single immutable state object* per screen,
and all changes flow through explicit *intents* reduced into a new state. Maximally
predictable and testable, excellent for complex screens; costs more boilerplate and a
single-state-object mindset. (Android's recommended pattern with Compose +
StateFlow leans MVI-ish.)

**TCA (The Composable Architecture).** A Swift/SwiftUI framework formalizing UDF with
explicit **State, Action, Reducer, and Effect** types, composable feature stores, and
first-class side-effect and dependency handling. Superb testability and composition;
opinionated, with a learning curve and runtime overhead. The "Redux for SwiftUI."

**Clean Architecture.** Orthogonal to the above: concentric layers (entities → use cases
→ interface adapters → frameworks) with the **dependency rule** — dependencies point
inward, the domain knows nothing of UI or frameworks. Often combined with MVVM/MVI for
the presentation layer. Great for large apps and testability; over-engineered for small
ones (layer/boilerplate tax).

These compose: a typical large app is *Clean layering + MVVM or MVI presentation +
UDF*, with **navigation**, **dependency injection** (Hilt/Koin on Android, manual or
Swinject/Factory on iOS), and **modularization** (feature modules with clear boundaries
for build speed, ownership, and reuse) as cross-cutting concerns.

## When to use / When NOT

- **MVVM — use when:** standard screens, platform-default tooling, a team that wants
  low ceremony. **Avoid when:** screens get complex enough that scattered mutable state
  causes bugs — tighten to MVI.
- **MVI — use when:** complex, stateful screens where predictability and replayable,
  testable state matter. **Avoid when:** the screen is trivial and the boilerplate isn't
  worth it.
- **TCA — use when:** a SwiftUI app wants rigorous UDF, composition, and exhaustive
  testing of state and effects. **Avoid when:** the team is small/new to the paradigm or
  the app is simple.
- **Clean — use when:** a large, long-lived, multi-team app needs strict boundaries and
  framework independence. **Avoid when:** a small app — the layers add cost without payoff.
- **Modularization — use when:** build times, team boundaries, and reuse justify it
  (most apps past a few features). **Avoid when:** a single small app — premature module
  splitting just adds friction.

## Tradeoffs

| Pattern | State shape | Predictability | Boilerplate | Testability | Best fit |
| ------- | ----------- | -------------- | ----------- | ----------- | -------- |
| MVVM | Observable props | Medium | Low | Good | Standard screens, platform default |
| MVI | Single immutable state | High | Medium–high | Excellent | Complex stateful screens |
| TCA | State + Action + Reducer | High | Medium–high | Excellent | Rigorous SwiftUI apps |
| Clean | Layered (orthogonal) | High (boundaries) | High | Excellent | Large, long-lived apps |

## Real-world examples

- **Android's official guidance** prescribes UDF with a `ViewModel` exposing a single
  `StateFlow<UiState>`, repositories behind the domain, and Hilt for DI — effectively
  MVVM/MVI + Clean.
- **Point-Free's TCA** powers many production SwiftUI apps that want exhaustive testing
  of state and effects.
- **Large apps (Uber, Airbnb, Spotify)** are heavily modularized with feature modules and
  strict layer boundaries for build speed and team autonomy.
- **Banking/fintech apps** lean on Clean layering and DI so the security-sensitive domain
  is framework-independent and exhaustively unit-tested apart from the UI.
