## Overview

Matching tells you *which* documents contain the query terms; **ranking** tells
you which ones to show *first*. With a million matches and a screen that fits
ten, ranking *is* the product. This page covers the two families that dominate
modern search. **Lexical** ranking scores by term overlap statistics — TF-IDF,
then its successor **BM25**, which is the default in essentially every search
engine today. **Semantic** ranking scores by *meaning* using **embeddings** and
nearest-neighbour search, so `"laptop that won't overheat"` can match a review
that never uses those words. Neither dominates everywhere, so the strongest
production systems run **hybrid** search and fuse the two rankings. We finish
with the levers on top: learning-to-rank, faceting, and boosting.

## Mental model

Ranking is a **scoring function over (query, document) pairs**; you sort by the
score and cut to top-K. The two families differ in what the score *measures*:

- **Lexical (BM25):** "how statistically surprising is it that this document
  contains *these exact terms* this many times?" Sparse, exact-token, explainable.
- **Semantic (vectors):** "how close is this document's *meaning vector* to the
  query's meaning vector?" Dense, fuzzy, captures synonymy and intent but can
  drift off literal terms.

Their failure modes are complementary. BM25 nails exact terms, product codes,
names, and rare keywords — but is blind to synonyms it wasn't told about and to
paraphrase. Vectors capture intent and synonymy — but can confidently return
something *about the right topic* yet missing the exact term you needed (a part
number, a person's name). **Hybrid** search exists because fusing two systems
that fail differently beats either alone.

## Types / Variants

**TF-IDF.** Score a term by **term frequency** (more occurrences in this doc →
more relevant) times **inverse document frequency** (rarer across the corpus →
more discriminating). Intuitive and historically dominant, but it has no
principled handling of document length and TF grows unboundedly — a doc that
repeats a word 100 times scores ~100× a single mention, which is rarely right.

**BM25 (Okapi BM25) — and why it won.** A probabilistic refinement of TF-IDF
that fixes its two flaws: **TF saturation** (the `k1` parameter makes the 10th
occurrence add far less than the 2nd — diminishing returns) and **length
normalization** (the `b` parameter discounts long documents so they don't win by
sheer size). It is robust, needs almost no tuning, and consistently outperforms
TF-IDF, which is why it is the **default in Lucene/Elasticsearch/OpenSearch/Solr
and Postgres-adjacent rankers**. If you do nothing, you get BM25, and that is the
right default.

**Vector / semantic search.** An **embedding model** maps text to a dense vector
(say 384–1536 dims) where semantic similarity ≈ geometric closeness (cosine /
dot product). At query time you embed the query and find its **nearest
neighbours** among document vectors. Exact kNN is O(N) per query, so production
uses **ANN (approximate nearest neighbour)** indexes — **HNSW** (graph-based, the
common default), **IVF** (inverted-file clustering), or **PQ** (product
quantization for memory) — trading a little recall for huge speed.

**Hybrid search (BM25 + vector).** Run both retrievers and **fuse** their result
lists. The robust, model-free fusion is **Reciprocal Rank Fusion (RRF)**: score
each doc by `Σ 1/(k + rank_in_each_list)`, which combines on *ranks* not on
incomparable raw scores (BM25 scores and cosine similarities live on different
scales — never add them directly). Alternatively, *linear combination* of
normalized scores, but RRF is simpler and remarkably strong.

**Learning-to-rank (LTR).** Replace the hand-tuned scoring with a model trained
on judged or click data. Usually a **two-stage** design: a cheap retriever (BM25
and/or vectors) fetches a few hundred candidates, then a learned reranker
(gradient-boosted trees like LambdaMART, or a cross-encoder transformer) reorders
the top set using rich features (BM25 score, freshness, popularity,
personalization, vector similarity). High ceiling, but needs training data and a
serving path.

**Faceting & filtering.** **Filters** are boolean constraints that *remove*
candidates without affecting the relevance score (in-stock, price < 100) — fast
and cacheable. **Facets** are the aggregated counts per value shown in the UI
("Brand: Sony (412)"). Filtering is recall control; ranking is the order of
what's left.

**Boosting.** Bias the score toward business goals: weight the `title` field over
`body`, boost fresher documents, lift in-stock or sponsored items, raise an exact
phrase over loose matches. Boosting is how product judgment enters an otherwise
statistical ranking — apply sparingly and measure, or you drown relevance in
business rules.

## When to use / When NOT

- **Use lexical (BM25) when:** queries are keyword-like; exact terms, names,
  codes, identifiers matter; explainability and zero-training simplicity matter;
  or the corpus is domain-specific where general embeddings are weak. **Avoid
  pure lexical when:** users phrase intent in words the documents never use
  (paraphrase, synonymy, natural-language questions).
- **Use semantic (vectors) when:** matching by meaning matters — Q&A, "find
  similar," recommendations, cross-lingual, or messy natural-language queries;
  and you can host an embedding model and an ANN index. **Avoid pure semantic
  when:** exact-term recall is non-negotiable (it may miss the literal keyword),
  latency/cost of embedding is prohibitive, or your domain is far from the
  embedding model's training distribution.
- **Use hybrid (BM25 + vector, RRF) when:** you want both exact-term precision
  and semantic recall and can afford two retrievers plus fusion — this is the
  modern default for high-quality search. **Avoid hybrid when:** the added
  complexity and second index aren't justified by measured relevance gains.
- **Add learning-to-rank when:** you have click/judgment data and relevance is a
  core metric worth a training+serving pipeline. **Skip LTR when:** you lack
  labels or BM25/hybrid already meets the bar — it is the last 10%, not the first.

## Tradeoffs

| Dimension | Lexical (BM25) | Semantic (vectors) | Hybrid (RRF) |
| --------- | -------------- | ------------------ | ------------ |
| Matches on | Exact terms / statistics | Meaning / intent | Both |
| Synonyms / paraphrase | Blind (unless told) | Strong | Strong |
| Exact codes / names | Strong | Can miss | Strong |
| Infra needed | Inverted index | Embedding model + ANN | Both |
| Cost / latency | Low | Higher (embed + ANN) | Highest |
| Explainability | High (term scores) | Low (opaque vector) | Mixed |
| Tuning / training | Minimal (works default) | Model choice matters | Fusion + both |
| Cold-start with no data | Works immediately | Works (pretrained) | Works |

## Real-world examples

- **Elasticsearch/OpenSearch/Solr** all default to **BM25** as the similarity and
  expose `k1`/`b` knobs; all now ship native **kNN/HNSW** vector fields and
  built-in **RRF** for hybrid retrieval.
- **Vespa** was built for two-phase ranking and runs lexical, vector, and
  learned rankers natively in one engine — a reference design for hybrid + LTR.
- **RAG pipelines** (retrieval-augmented generation for LLMs) almost universally
  use hybrid retrieval + a reranker to feed the most relevant chunks to the model.
- **E-commerce search** (Amazon-class) layers BM25 + vectors + learning-to-rank
  with heavy boosting for availability, margin, and personalization.
