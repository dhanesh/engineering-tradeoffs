## Overview

Data pipelines that work on a gigabyte often fall over — or quietly cost a
fortune — on a terabyte. Scaling them is mostly about understanding what's
expensive (moving data between machines), what wastes money (idle compute,
redundant scans, millions of tiny files), and what you can trade (freshness for
cost). Unlike app scaling, where latency per request dominates, data-pipeline
scaling is about **throughput, data movement, and the cloud bill** — and the
bill is often the loudest signal that something is wrong.

This page covers **partitioning and parallelism**, why **shuffle** is the
expensive part of distributed processing, **data skew**, the **small-files
problem** and **compaction**, **cost optimization** via compute/storage
separation, the **freshness-vs-cost** tradeoff, and governing **PII at scale**.
It assumes the storage and pipeline pages.

## Mental model

Distributed data processing is **embarrassingly parallel until it has to move
data across the network** — and that movement, the **shuffle**, is where the
time and money go. The mental model has three pieces:

1. **Partition to parallelize.** Split data into independent chunks so N workers
   process them simultaneously. Throughput scales with parallelism — *if* the
   chunks are balanced and independent.
2. **Shuffle is the tax.** Operations that need data grouped differently than
   it's partitioned (`GROUP BY`, `JOIN`, `DISTINCT`, repartition) force a
   **shuffle**: every worker sends data to every other worker over the network,
   with serialization and often disk spill. Shuffle is usually the single most
   expensive step; minimizing and avoiding it is the core of pipeline
   performance tuning.
3. **Skew breaks parallelism.** If one partition (one hot key — a null, a
   mega-customer) is far larger than the rest, one worker does most of the work
   while others idle. The job runs as slow as its biggest partition. **Data
   skew** is the most common reason a "parallel" job isn't.

Hold this: **partitioning gives you parallelism; shuffle and skew take it
away.**

## Types / Variants

**Partitioning / parallelism strategies.** Hash partitioning (even spread by
key), range partitioning (ordered, good for time), and partition *count* tuning
(too few starves parallelism; too many creates overhead and small files). Good
partitioning aligns with query filters so the engine prunes whole partitions.

**Shuffle-reduction techniques.**
- *Broadcast join* — when one side is small, send it in full to every worker so
  the join needs no shuffle of the big side. Often a 10x win.
- *Pre-partitioning / bucketing* — store data already partitioned by the join/
  group key so repeated operations skip the shuffle.
- *Pushing filters/aggregations down* — reduce data volume *before* the shuffle.

**Skew mitigation.**
- *Salting* — append a random suffix to hot keys to split them across workers,
  then aggregate in two stages.
- *Isolating hot keys* — handle the mega-key separately.
- *Adaptive query execution* (Spark AQE) — detect and split skewed partitions
  at runtime.

**The small-files problem.** Streaming/incremental ingestion and over-
partitioning produce millions of tiny files. Each file carries metadata and
open/read overhead, so queries spend more time listing and opening files than
reading data — performance collapses and metadata operations time out. The fix
is **compaction**: periodically rewrite many small files into fewer large ones
(Iceberg/Delta/Hudi have built-in compaction / `OPTIMIZE`). The dual sin is
*over-compaction* or too-coarse partitions that hurt pruning — balance file
size (commonly ~128MB–1GB) against partition granularity.

**Compute/storage separation.** Modern platforms (Snowflake, BigQuery,
lakehouses) decouple cheap object storage from elastic, independently-scaled
compute. You pay for storage continuously and compute only while querying, can
spin compute up/down per workload, and avoid paying for idle clusters — the
biggest structural cost lever.

## When to use / When NOT

- **Add partitions/parallelism — when:** a job is CPU/IO-bound on a single
  worker and the data splits cleanly. **Avoid** over-partitioning into tiny
  chunks — overhead and small files erase the gains.
- **Broadcast join — when:** one side fits comfortably in worker memory; it
  removes a shuffle. **Avoid** when both sides are large (broadcast OOMs).
- **Salt / mitigate skew — when:** one or few hot keys dominate a partition and
  one task lags badly. **Avoid** blanket salting when data is already balanced —
  it adds a second aggregation stage for nothing.
- **Compact — when:** file counts balloon from streaming/incremental writes and
  query/metadata latency rises. **Avoid** compacting so aggressively that you
  lose useful partition pruning, and schedule it off-peak (it rewrites data).
- **Separate compute/storage / tier to cheap freshness — when:** cost matters
  and not every dataset needs sub-minute freshness. **Avoid** paying for
  streaming/standing compute on data that a daily batch would serve fine.

## Tradeoffs

The defining tension is **data freshness vs cost.** Fresher data means more
frequent runs, standing streaming infrastructure, smaller (more numerous)
files, and more compute — each a cost multiplier. Staler data batched less often
is dramatically cheaper. Most "we need real-time" requirements dissolve under
the question *"what decision changes if this is 1 hour old instead of 1
minute?"* — and the honest answer usually permits cheaper batch.

| Lever | Cheaper / slower end | Costlier / fresher end |
| ----- | -------------------- | ---------------------- |
| Cadence | Daily batch | Continuous streaming |
| File layout | Compacted large files | Many small fresh files |
| Compute | Off when idle, separated | Always-on standing cluster |
| Partitioning | Coarse (good pruning) | Fine (parallel but small files) |
| Reprocessing | Full refresh (simple, costly) | Incremental (cheap, complex) |

Two more cross-cutting concerns:
- **Shuffle/skew are pure waste** to be engineered out — broadcast joins,
  pushdown, salting, AQE. Reducing them is almost always a strict win (faster
  *and* cheaper), unlike the freshness tradeoff which is a genuine choice.
- **PII at scale** is a governance cost that grows with data: identify and tag
  sensitive columns (catalog/lineage), apply column masking / tokenization,
  enforce row/column access policies, retention/deletion (right-to-be-forgotten),
  and audit access. For a fintech handling loan and payment data, this is not
  optional — it must be wired into the platform (masking on land or in-warehouse
  policies) rather than bolted on per pipeline.

## Real-world examples

- **Spark's Adaptive Query Execution** detects skewed partitions and splits
  them at runtime — a direct answer to the most common scaling failure.
- **Iceberg / Delta / Hudi compaction** (`OPTIMIZE`, rewrite-data-files) is
  standard practice to tame the small-files problem from streaming ingestion.
- **Snowflake and BigQuery** built their economics on compute/storage
  separation, letting teams pay for compute only while querying.
- **Fintechs and healthcare platforms** enforce column masking, tokenization,
  and access policies on PII at the warehouse/lakehouse layer (e.g. via Unity
  Catalog or BigQuery column-level security) to meet regulatory obligations at
  scale.
