## Overview

DNS is the Internet's distributed phone book: it turns human names (`api.example.com`)
into the addresses machines route to (`93.184.216.34`). But it's far more than a lookup —
it's also a **control plane**. Because every client asks DNS *first*, before any
connection, DNS is where you steer traffic: to the nearest region (GeoDNS), away from a
failed datacenter (failover), across a fleet (round-robin), or to whichever service
instance is healthy (service discovery). It's also a giant, layered **cache** governed by
TTLs — which makes it fast but means changes propagate slowly, the source of countless
"but I updated the record an hour ago" incidents. This page covers how resolution works,
what each record type does, and how to wield DNS as a routing and discovery tool.

## Mental model

**DNS is a delegated hierarchy resolved by one tireless intermediary.** Names are a tree
read right-to-left: the **root** (`.`) delegates `com` to **TLD** servers, which delegate
`example.com` to that domain's **authoritative** servers, which hold the actual records.
No single server knows everything; each only knows who to ask next. A **recursive
resolver** (your ISP's, or 8.8.8.8) is the concierge who does the legwork for you: you
ask it once, and it walks root → TLD → authoritative on your behalf, caching every answer
so the next person's lookup is instant.

The second half of the model is **caching with an expiry clock**: every record carries a
**TTL**. Resolvers serve cached answers until the TTL elapses, so a low TTL means fast
propagation but more queries, while a high TTL means efficiency but slow change. This
single number is the lever behind every DNS-based failover and migration decision.

## Types / Variants

**Recursive vs iterative resolution.**
- **Recursive**: the client asks a resolver for the final answer and the *resolver* does
  all the work, querying each level itself and caching results. What end hosts use.
- **Iterative**: each server replies with a *referral* ("I don't know, but ask this TLD
  server") and the *asker* follows the chain. This is how the recursive resolver talks to
  root/TLD/authoritative servers internally.

**The server hierarchy.** **Root** (13 logical root server letters, massively
anycast-replicated) → **TLD** (`.com`, `.org`, ccTLDs) → **Authoritative** (the domain
owner's nameservers, the source of truth). Resolvers cache at every level.

**Record types (the common ones):**
- **A / AAAA** — name → IPv4 / IPv6 address.
- **CNAME** — alias one name to another (can't coexist with other records at the apex;
  use ALIAS/ANAME or flattening at the zone apex).
- **MX** — mail server + priority.
- **NS** — delegates a zone to its authoritative nameservers.
- **TXT** — arbitrary text; carries SPF/DKIM/DMARC and domain-ownership proofs.
- **SRV** — service location (host + port + priority/weight) — explicit service discovery.
- **PTR** — reverse lookup (IP → name).
- **SOA** — zone metadata (serial, refresh, default TTL).
- **CAA** — which CAs may issue certs for the domain.

**Caching & TTL.** Answers are cached at the OS stub resolver, the recursive resolver,
and sometimes the app. TTL governs lifetime. **Negative caching** (NXDOMAIN) is cached
too. Lower the TTL *before* a planned migration so changes propagate fast when you cut
over.

**Anycast.** One IP address announced from many locations; routing delivers each client
to the topologically nearest instance. Powers resilient root servers, public resolvers
(1.1.1.1, 8.8.8.8), and CDNs — it's how a single address survives a regional outage and
serves locally.

**GeoDNS / latency-based routing.** The authoritative server returns *different* answers
depending on the resolver's location/latency, steering users to the nearest region. The
front door of global traffic management.

**DNS as load balancing & service discovery.** Multiple A records for one name spread
clients across servers (**round-robin DNS** — cheap but crude: no health awareness,
honors client caching). Managed DNS adds **health checks + failover** (drop a dead
endpoint from answers). Internally, **SRV records** and systems like **Consul**,
**CoreDNS** (Kubernetes), and **Route 53** turn DNS into a service registry.

**Transport.** UDP/53 for the common small query (fast, retry on loss), TCP/53 fallback
for large responses (zone transfers, DNSSEC). **DoT/DoH** (DNS over TLS/HTTPS) encrypt
queries for privacy.

## When to use / When NOT

- **Use round-robin DNS when:** you want dead-simple, free spreading across a few stable
  endpoints and clients tolerate uneven distribution. **Avoid it as your only LB when:**
  you need health awareness or fast failover — client caching means a dead IP keeps
  getting handed out until TTL expires. Pair with a real load balancer.
- **Use GeoDNS / latency routing when:** you run multi-region and want users hitting the
  nearest stack with no client logic. **Avoid relying on it for fine-grained balancing:**
  it resolves at *resolver* granularity (many users behind one resolver get one answer)
  and caches — it's coarse steering, not per-request balancing.
- **Use anycast when:** you need a single global IP that's both fast and outage-resilient
  (resolvers, CDNs, edge). **Avoid anycast for stateful long-lived connections** unless
  the service is truly stateless per-PoP — route flaps can move a flow mid-connection.
- **Use low TTLs when:** about to migrate or for endpoints that fail over. **Avoid
  permanently low TTLs:** they multiply query load and lose caching benefit; raise them
  back after a cutover.
- **Use DNS-based service discovery (SRV/CoreDNS/Consul) when:** inside a dynamic
  cluster. **Avoid hand-managed records** for ephemeral instances — automate it.

## Tradeoffs

| Technique | Pros | Cons |
| --------- | ---- | ---- |
| Round-robin DNS | Free, simple, spreads load | No health checks; client caching skews/delays |
| GeoDNS / latency routing | Nearest region, no client logic | Resolver-granularity, cached, coarse |
| Anycast | One IP, fast + outage-resilient | Flaps can move connections; harder to debug |
| Managed DNS + health checks | Real failover, drops dead endpoints | Vendor lock-in, cost, still TTL-bounded |
| Low TTL | Fast propagation / failover | More queries, less caching benefit |
| High TTL | Efficient, fewer lookups | Slow to change; stale during incidents |

## Real-world examples

- **Cloudflare 1.1.1.1** and **Google 8.8.8.8** are massively **anycast** public
  recursive resolvers — one IP, served from hundreds of locations.
- **AWS Route 53** offers latency-based, geolocation, weighted, and failover routing with
  health checks — DNS as a full traffic-management control plane.
- **Kubernetes** uses **CoreDNS** for in-cluster service discovery: `svc.namespace.svc.cluster.local`
  resolves to service IPs, with SRV records for ports.
- **HashiCorp Consul** exposes the service catalog over DNS, so apps discover healthy
  instances with a plain lookup.
