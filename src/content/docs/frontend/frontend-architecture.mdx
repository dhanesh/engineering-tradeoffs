## Overview

Frontend architecture is the set of structural decisions that determine whether a
codebase stays maintainable as it and the team grow: how components compose, how
styles are scoped, how code is organized across packages, how it is built, and
which framework underpins it all. These choices are sticky — changing a CSS
strategy or splitting a monolith into micro-frontends mid-life is expensive — so
they reward thinking about *team size, deploy independence, and longevity* up
front rather than chasing the newest tool. The recurring trap is adopting
big-company architecture (micro-frontends, complex monorepos) at small-company
scale, paying the coordination cost without the coordination problem.

## Mental model

Frontend architecture is **scope management at four levels**: scoping *markup*
(components), scoping *styles* (CSS strategy), scoping *code ownership*
(repo/package boundaries), and scoping *deployment* (one app vs many). At each
level you trade **isolation against integration cost**: tighter isolation
(scoped CSS, separate packages, independently deployed micro-frontends) reduces
the blast radius of a change and lets teams move independently, but adds
boundaries, duplication, and coordination overhead. The right level of isolation
is a function of how many people touch the code and how independently they must
ship — not of fashion. A two-person team wants the least isolation that keeps
things tidy; a fifty-team org wants the most.

## Types / Variants

**Component architecture and design systems.** Compose UI from small, reusable,
single-responsibility components. A **design system** is the shared library of
those components plus tokens (color, spacing, type) and usage rules — the
contract that keeps a large UI consistent. Patterns like composition over
configuration and headless components (logic without styling) keep them reusable.

**CSS approaches:**

- **BEM (Block-Element-Modifier).** A naming convention (`card__title--active`)
  for scoping in plain CSS. Zero tooling, but discipline-dependent and verbose.
- **CSS Modules.** Build-time local scoping — class names are hashed per file, so
  collisions are impossible. Plain CSS ergonomics with guaranteed scope.
- **Utility-first (Tailwind).** Compose styles from atomic utility classes in
  markup. Fast iteration, tiny shipped CSS (purged), consistent by constraint;
  cost is verbose markup and a learning curve.
- **CSS-in-JS (styled-components, Emotion).** Styles co-located in JS, scoped and
  dynamic. Great DX and dynamic theming; runtime cost and SSR complexity pushed
  many teams toward zero-runtime alternatives (vanilla-extract, Linaria).

**Monorepos.** One repository, many packages (apps, shared libs, design system),
managed with tooling (Nx, Turborepo, pnpm workspaces). Atomic cross-package
changes, shared config, easy code sharing; cost is build orchestration and CI
complexity. The alternative is polyrepo — independent repos, simpler each but
hard to change across.

**Micro-frontends.** Splitting one app into independently developed and deployed
pieces owned by different teams, composed at runtime (Module Federation),
build time, or via an app shell. Enables team autonomy at large scale; costs
duplicated dependencies, version skew, runtime integration risk, and harder
shared state. Rarely justified below many teams.

**Build tooling (bundlers).** Vite (esbuild dev + Rollup build) is the modern
default for speed; webpack remains common in large legacy apps and powers Module
Federation; esbuild/Rollup/Turbopack occupy specific niches. The bundler handles
splitting, tree shaking, and asset transforms.

**The BFF (Backend for Frontend).** A thin server tailored to one frontend that
aggregates and reshapes backend/microservice calls into exactly what the UI
needs — removing client-side orchestration, hiding internal APIs, and handling
auth. See *API gateways and BFF*.

**Framework selection.** React (ecosystem, hiring), Vue (gentle, cohesive),
Svelte (compile-away, minimal runtime), Solid (fine-grained signals), Angular
(batteries-included for large orgs), and meta-frameworks (Next, Nuxt, SvelteKit,
Astro) that add routing/SSR.

## When to use / When NOT

- **Use a design system when:** multiple teams or many surfaces must stay
  consistent. **Avoid building one** for a single small app — a folder of
  components is enough.
- **Use a monorepo when:** packages change together and share code (app + design
  system + utils). **Avoid it when:** projects are truly independent and the
  build orchestration cost outweighs the sharing benefit.
- **Use micro-frontends when:** many autonomous teams must deploy independently on
  one product and the org-coordination pain is real. **Avoid them when:** you have
  one or a few teams — you will pay duplication, version skew, and integration
  risk for autonomy you do not need.
- **Use utility-first CSS when:** you want fast, consistent, low-runtime styling
  and accept verbose markup. **Avoid CSS-in-JS runtime libraries when:** SSR
  performance is critical — prefer modules or zero-runtime.
- **Use a BFF when:** the client orchestrates many backend calls or needs reshaped
  data. **Avoid it when:** a single well-shaped API already serves the UI.
- **Pick a mainstream framework when:** hiring and ecosystem matter. **Avoid
  niche/bleeding-edge** for long-lived business-critical apps unless the team
  owns that expertise.

## Real-world examples

- **Spotify** popularized organizing UI work around autonomous squads, an early
  driver of the micro-frontend conversation — though many teams later found a
  well-structured monolith simpler.
- **Material UI, Radix, and shadcn/ui** show the spectrum from full design system
  to headless primitives to copy-in components teams own outright.
- **Tailwind CSS** became the dominant utility-first approach by shipping near-zero
  CSS after purge while enforcing a consistent design scale.
- **Vite** displaced webpack as the default bundler for new projects on dev-server
  speed, while **webpack Module Federation** remains the main runtime mechanism
  for micro-frontends.
