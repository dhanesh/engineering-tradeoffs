## Overview

Most frontend complexity is *state* complexity: who owns a piece of data, who can
change it, who needs to re-render when it changes, and how it stays consistent
with the server. Reaching for Redux on day one is the classic over-engineering
mistake; refusing to ever lift state is the classic under-engineering one. The
skill is **classifying each piece of state** — is it local UI state, shared
client state, server-cache state, or URL state? — because each class has a
right tool, and most apps need different tools for different state, not one
store to rule them all.

## Mental model

Think of state in **four buckets**, each answering "where does the truth live?":

1. **Local state** — owned by one component (a toggle, an input's value).
   Truth lives in the component. Use `useState`.
2. **Shared client state** — UI state several components need (theme, a modal's
   open flag, a multi-step form). Truth must live *above* them. Lift it, or use
   context / a store.
3. **Server state** — a cached copy of data the server owns (user profile, a
   product list). The truth lives on the *server*; the client holds a possibly
   stale copy that needs fetching, caching, revalidation, and invalidation.
   This is not "state" in the same sense — it is a cache, and treating it like
   local state (manually stuffing fetch results into Redux) is the #1 source of
   stale-data bugs.
4. **URL state** — state that belongs in the address bar (current page, filters,
   selected tab, search query). The truth lives in the URL so it is shareable,
   bookmarkable, and survives reload.

Picking the wrong bucket is the root cause of most state pain. Server data in a
global store goes stale; URL-worthy state in component state breaks the back
button; local state lifted too high causes needless re-renders.

## Types / Variants

- **`useState` / `useReducer` (local).** Built-in, zero deps. `useReducer` when
  transitions are complex or many actions mutate one object.
- **Prop drilling.** Passing state down through props. Fine for two or three
  levels; painful and brittle beyond that.
- **Context API.** Broadcasts a value to a subtree without drilling. Solves
  *prop drilling*, not *state management* — every consumer re-renders on any
  change, so it suits low-frequency, slowly-changing values (theme, locale,
  auth user), not hot state.
- **Flux / Redux.** A single immutable store, state changed only via dispatched
  actions through pure reducers. Predictable, time-travel debuggable, great for
  complex shared client state with many interdependent updates. Heavy boilerplate;
  Redux Toolkit reduces it. Often misused as a server cache.
- **Atomic stores (Zustand, Jotai, Recoil).** Lighter global state without the
  reducer ceremony; subscribe to slices so only affected components re-render.
- **Signals (Solid, Preact, Angular, Vue refs).** Fine-grained reactive
  primitives: a signal is a value plus its dependents, so an update re-runs only
  the exact computations that read it — no virtual-DOM diff, no re-render of an
  entire component tree.
- **Server-state libraries (TanStack Query, SWR, Apollo, RTK Query).** Purpose-built
  for bucket 3: caching, deduping requests, background refetch, stale-while-
  revalidate, optimistic updates, and invalidation. This is what you should reach
  for instead of putting fetch results in a global store.
- **Derived state.** State *computed* from other state (a filtered list, a total).
  The rule: do not store it — derive it on render (or memoize). Storing derived
  state creates two sources of truth that drift.
- **URL as state.** Router params and query strings hold shareable state. The
  router *is* a store for the subset of state that should survive a reload.

## When to use / When NOT

- **Use local state when:** only one component (or it and a child via props)
  cares. **Avoid lifting** until a second component genuinely needs it — premature
  lifting causes re-render cascades.
- **Use Context when:** a slowly-changing value is needed widely (theme, auth).
  **Avoid Context for** high-frequency updates (mouse position, form keystrokes) —
  it re-renders every consumer.
- **Use a server-state library when:** the data lives on the server. **Avoid a
  global store for server data** — you will reimplement caching, badly.
- **Use Redux / a store when:** you have substantial, interdependent *client*
  state with complex update logic and need traceability. **Avoid it when:** your
  "global state" is mostly server data plus a couple of toggles — that is
  TanStack Query plus `useState`.
- **Use signals when:** fine-grained reactivity and minimal re-rendering matter,
  and your framework supports them. **Avoid retrofitting** them into an
  architecture built around immutable top-down renders.
- **Use the URL when:** state should be shareable, bookmarkable, or survive
  reload (filters, tabs, pagination). **Avoid the URL for** transient or
  sensitive state.

## Real-world examples

- **TanStack Query (React Query)** popularized the server-state-as-cache model;
  most modern React apps now pair it with light local/global state instead of a
  monolithic Redux store.
- **Redux** still anchors large, long-lived apps with intricate cross-cutting
  client state; **Redux Toolkit** is the official, boilerplate-reduced default.
- **SolidJS and Angular signals** brought fine-grained signal reactivity
  mainstream — updates touch only the exact DOM bindings that read the signal.
- **Next.js and Remix** push more state into the **URL and server**, shrinking
  client state to genuinely interactive bits — search params as the filter store
  is now an idiomatic pattern.
