## Overview

Frontend performance is a business metric: every 100 ms of added latency
measurably lowers conversion, and Google ranks partly on it. The discipline has
converged on **Core Web Vitals** — three field-measured numbers that proxy
loading, interactivity, and visual stability. Optimizing them is mostly about
shipping *less* (smaller bundles, fewer bytes on the critical path), shipping it
*later* (code splitting, lazy loading), and *not moving things around* after
paint. The cardinal rule: measure with real-user field data first, because lab
tools lie about the conditions your actual users face.

## Mental model

Performance is a **budget you spend on bytes and main-thread time**. The browser
has one main thread; every kilobyte of JavaScript must be downloaded, parsed,
compiled, and executed on it before the page responds — and JS is byte-for-byte
*far* more expensive than images or CSS because of that parse/execute tax. So the
mental model is two ledgers:

- **The network ledger** — total bytes, and crucially *which bytes are on the
  critical path*. Defer or split everything not needed for the first interaction.
- **The main-thread ledger** — time spent parsing/executing JS and doing
  layout/paint. Long tasks here block input (hurting INP) and delay
  interactivity.

Core Web Vitals map onto experience: **LCP** = "did the main content appear
fast?" (loading), **INP** = "does it respond quickly when I interact?"
(responsiveness), **CLS** = "did it stay put?" (stability).

## Types / Variants

The three Core Web Vitals and their good thresholds (75th percentile, field):

- **LCP (Largest Contentful Paint) — good is under 2.5 s.** Time until the
  largest content element (hero image, headline) is painted. Driven by TTFB,
  render-blocking resources, and the LCP resource's load time. Fix with faster
  server response, `preload` of the LCP image, smaller critical CSS.
- **INP (Interaction to Next Paint) — good is under 200 ms.** Replaced FID in
  March 2024. Measures the latency of *all* interactions across the page's
  lifetime (the worst, roughly), from input to the next paint. Driven by
  long main-thread tasks. Fix by breaking up long tasks, yielding to the event
  loop, debouncing, and reducing hydration cost.
- **CLS (Cumulative Layout Shift) — good is under 0.1.** Sum of unexpected layout
  shifts. Driven by images/ads/iframes without reserved dimensions, late-loading
  fonts, and content injected above existing content. Fix with explicit
  `width`/`height` (or `aspect-ratio`), `font-display: optional`, and reserving
  space for dynamic content.

The main optimization techniques:

- **Code splitting** — break the bundle so each route/feature loads its own
  chunk on demand (dynamic `import()`), shrinking the initial payload.
- **Lazy loading** — defer offscreen work: `loading="lazy"` on images/iframes,
  `import()` on components below the fold or behind interaction.
- **Tree shaking** — the bundler drops unused exports (relies on ES modules and
  no side effects); import named functions, not whole libraries.
- **Critical CSS** — inline the CSS needed for above-the-fold content, defer the
  rest, so the first paint is not render-blocked on a full stylesheet.
- **Image optimization** — modern formats (AVIF, WebP), responsive `srcset`,
  correct dimensions, and CDN resizing. Images are usually the largest bytes.
- **Preload vs prefetch** — `preload` fetches a resource needed for the *current*
  navigation at high priority (the LCP image, a critical font); `prefetch`
  fetches at low priority something likely needed for a *future* navigation.
- **Caching** — HTTP caching and a CDN keep repeat visits and shared assets fast
  (see *CDN and edge caching* and *Caching strategies*).

## When to use / When NOT

- **Use code splitting when:** the app has distinct routes/features not all needed
  upfront. **Avoid over-splitting** — too many tiny chunks add request overhead
  and waterfalls.
- **Use lazy loading when:** content is below the fold or behind interaction.
  **Avoid lazy-loading the LCP element** — it delays the very thing LCP measures;
  `preload` it instead.
- **Use `preload` when:** a critical resource is discovered late (a font in CSS,
  an LCP image set by JS). **Avoid preloading everything** — it competes for
  bandwidth and can *slow* the true critical resource.
- **Use `prefetch` when:** you can predict the next navigation (hovered link,
  likely next step). **Avoid prefetching aggressively** on metered/mobile
  connections.
- **Optimize CLS reservations when:** you have images, ads, or async content.
  **Avoid** inserting content above existing content after load.

## Real-world examples

- **Google Search ranking** uses Core Web Vitals as a signal, and the
  **Chrome User Experience Report (CrUX)** publishes the real-user field data
  that defines "good."
- **Next.js / Astro image components** automate format negotiation (AVIF/WebP),
  responsive `srcset`, and dimension reservation — fixing LCP and CLS by default.
- **The INP transition (March 2024)** pushed teams to profile long tasks and
  break up hydration — frameworks responded with selective and progressive
  hydration.
- **Lighthouse and WebPageTest** give lab diagnostics (reproducible, controlled),
  while CrUX/RUM give field truth — mature teams use lab to debug, field to
  judge.
